# План проекта: ИИ-ассистент по размещению «Синоникса»

Стек: TypeScript (Node 24), npm workspaces, React + Vite, Fastify, vitest. Запуск локально.
Модель/API: выбирается позже (OpenRouter, входной тариф ≤ $0,10/млн у **каждой** модели контура). До выбора слой LLM работает через интерфейс с заглушкой.

## 1. Принцип архитектуры

LLM делает только то, что нельзя сделать кодом:

1. **Извлечение** — свободный текст → список операций над состоянием сессии (`Op[]`, строгий JSON).
2. **Классификация намерения** — описание задачи / ответ на вопрос / вопрос о текущей схеме / правка / вопрос о продукте / вне темы.
3. **Ответ на вопрос о продукте** — по найденным фрагментам базы знаний, со ссылкой «файл, раздел».

Всё остальное — детерминированный код в `packages/core`:
подсчёт правил, режимы, размещение, вопросы с вариантами, статусы, файловые пользователи, JSON, текст объяснения.
Из одного `EngineResult` строятся таблица, JSON, `.drawio` и картинка в UI → они всегда согласованы.

```
сообщение ─► LLM(extract) ─► Op[] ─► core.applyOps ─► core.evaluate ─► EngineResult
                                                         │
ответ на карточку вопроса (клик) ─► core.answerToOps ────┘   (без LLM — бесплатно и быстро)
                                                         ▼
                              таблица · объяснение · JSON · diagram.toDrawio · viewer
```

Цель по стоимости: 1 вызов LLM на свободное сообщение, 0 вызовов на клик по варианту ответа,
+1 вызов только для вопросов о продукте. Эмбеддинги не используем (BM25 по заголовкам md).

## 2. Структура репозитория

```
synonyx-assistant/
  packages/core/      состояние, операции, движок правил, вопросы, экспорт JSON, объяснение  ← готово (v0)
  packages/diagram/   раскладка + mxfile XML в стиле 06_template.drawio
  packages/kb/        нарезка synonyx_base/*.md по заголовкам, BM25, ссылки «файл § раздел»
  packages/llm/       клиент OpenRouter (usage: include), журнал JSONL, снимок тарифов, расчёт стоимости
  apps/server/        Fastify API: сессии, сообщения, ответы на вопросы, экспорт
  apps/web/           React: старт, чат, карточки вопросов, вкладки результата, расходы
  config/models.json  id моделей, ссылки на карточки OpenRouter, тарифы, дата снимка
  kb/                 копия synonyx_base (md + drawio-шаблоны)
  docs/               архитектура, API, ограничения
```

## 3. Контракты (фиксируем в первый день, дальше не ломаем)

- **Состояние сессии** — `packages/core/src/types.ts` (`SessionState`, `DataFlow`, `FileFlow`).
  Тройное значение параметра `Maybe<T> = T | null | 'unknown'`:
  `null` — ещё не выяснено (задаём вопрос), `'unknown'` — пользователь ответил «не знаю» (не спрашиваем снова, результат предварительный).
- **Операции** — `packages/core/src/ops.ts` (`Op`). Это же JSON-схема ответа LLM.
- **Результат** — `EngineResult` (статус, правила, вопросы, неизвестные, допущения, объяснение, источники).
- **Служебный JSON** — `packages/core/src/export.ts` (`toResultJson`), совместим с `result.example.json`.

API сервера (черновик):

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/sessions` | новая сессия |
| POST | `/api/sessions/:id/messages` | свободный текст пользователя |
| POST | `/api/sessions/:id/answers` | ответы на карточки вопросов `{questionId, value \| 'unknown' \| {other: text}}[]` |
| GET  | `/api/sessions/:id` | состояние + последний корректный результат + история |
| GET  | `/api/sessions/:id/result.json` | служебный JSON |
| GET  | `/api/sessions/:id/diagram.drawio` | актуальная схема |
| GET  | `/api/sessions/:id/log.jsonl` | журнал вызовов моделей и времени шагов |

| Ты (ведущий) | `core` + `llm` + `server` | эталоны проходят тесты; цикл «сообщение → вопросы → результат → правка» работает |

## 5. План по дням

**День 1.** Контракты · движок правил + тесты на эталонах (F01, F02, F04, F07, N01, N05, U01, U02) ·
генератор drawio для F02/F07 · каркас UI на моковом `EngineResult` · клиент OpenRouter с журналом (если модель выбрана).

**День 2.** Промпт извлечения → `Op[]` · полный цикл с уточнениями · правки после результата (U03 целиком) ·
поиск по базе + ответы о продукте (Q01, Q10, O01) · просмотрщик схемы в UI · блок расходов.

**День 3.** Прогон всех сценариев и вариаций (3 сети, две открытые сети, «не знаю», неподдерживаемое) ·
замер времени шага (≤ 15 с) · бонусы (файловые пользователи, выгрузка `requests_for_vendor`) ·
README, `.drawio` + JSON по открытым сценариям, выгрузка журнала, демо.

## 6. Ловушки, которые проверяют (держим в тестах)

- Ответ на Modbus-запрос не отдельное правило; MQTT / Modbus TCP / МЭК 104 — всегда двунаправленные.
- NTP — одно однонаправленное правило к защищаемой сети, число устройств не важно, порт не угадываем.
- Несколько отправителей → одно правило; другой получатель / порт / протокол → отдельное.
- Файлы: SFTP и SMB на разных сторонах — одно правило; PULL на обеих сторонах → 2; PULL+PUSH на одном узле → 2;
  разные проверки на противоположных узлах → не делят правило; изоляция групп → делит.
- USB — только Узел А, мимо МЭ. Встроенного антивируса нет (→ ICAP + `requests_for_vendor`).
- Не выдумываем порт/протокол/направление/проверки. «Не знаю» → «Предварительная оценка: минимум N правил».
- 3+ сети → объяснить рамки, предложить пару. Обе открытые → спросить защищаемую сторону, зафиксировать как допущение.
- «Доступ ко всей подсети» → отказ правки, последнее корректное решение сохраняется.
- Вопрос о схеме не меняет конфигурацию; неоднозначная правка → уточнение.
- Стоимость: не «$0,00», не подставлять ноль при неизвестном usage, не удваивать usage одного call_id.
